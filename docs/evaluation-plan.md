## Reproducible fixture set

Use 128 unique synthetic records: 120 valid records in the main benchmark and eight invalid records in separate rejection fixtures. Store a versioned scenario manifest with stable record IDs, hidden obligation IDs, intended normalized keys, independently calculated totals, expected candidate memberships, validity labels, and reasons. Hidden labels never enter the application import.

Freeze the manifest before implementing the detector. Use a deterministic generator specification with fixed version `invoice-fixtures-v1`, seed `20261021`, stable sorting by record ID, fixed dates, UTF-8/LF output, and no wall-clock input. Record file hashes when artifacts are actually generated; no hashes or generator are claimed here. A separate reviewer should verify totals and labels without calling production rules.

Both members of two repeated-obligation pairs have a mismatch, giving four overlapping rows. Expected output: 32 finding objects involving 40 distinct valid rows. Duplicate groups include all members, so there is no presumed original row to count as a false positive.

The 12 near-duplicate pairs comprise four with the same number/different vendors, four with the same vendor/date/amount but different numbers, and four with significant punctuation/leading-zero differences. The two same-key legitimate reuse pairs represent different obligations in different periods; they deliberately expose the rule's false alerts and should be human-dismissed.

Standalone mismatch cases: four one-cent-high totals, four one-cent-low totals, four omitted-shipping totals, four totals adding rather than subtracting the discount. Include zero fields and `0.10 + 0.20 = 0.30` among valid controls. Add separate boundary fixtures for the maximum supported amount and a group of three matching records; these do not alter the main benchmark denominators.

## Validation cases

Eight separate one-row invalid fixtures: missing vendor ID, missing invoice number, non-USD currency, three-decimal total, formatted subtotal (`$1,234.56`), negative tax, impossible calendar date, and blank total. Each must reject its whole file with a precise row/field reason and no persisted invoices/findings.

Also assemble a mixed 128-row file using all records. Under the atomic import policy it must be rejected entirely: zero accepted rows, not 120 accepted and eight silently discarded. Evaluate the 120-row valid benchmark separately. Test malformed quoting, missing/duplicate/extra headers, duplicate record IDs, too many rows, oversize bytes, and empty files as independent rejection fixtures. Exclude rejected files from rule-performance denominators.

## Metrics and units

Report raw TP, FP, FN, TN with a clearly stated evaluation unit; precision = TP/(TP+FP), recall = TP/(TP+FN), false-positive rate = FP/(FP+TN). Undefined ratios are `N/A`, not zero. For duplicate groups, exact membership matching is necessary; a partial or oversized group is incorrect.

| Evaluation | Unit / denominator | Planned expected result |
| --- | --- | --- |
| Duplicate rule conformance | Expected normalized-key groups, exact membership | Exactly 12 groups; no missing/extra groups |
| Semantic duplicate retrieval | All unordered pairs among 120 valid records: 7,140 pairs; ten genuine repeated obligations | TP 10, FP 2, FN 0, TN 7,128; precision 83.33%, recall 100%, pair FPR about 0.028% |
| Difficult duplicate negatives | 12 near-duplicate pairs plus two legitimate same-key reuse pairs | Two false alerts among 14 designated negative pairs; report alongside aggregate FPR |
| Total mismatches | 120 valid records: 20 positive, 100 negative | TP 20, FP 0, FN 0, TN 100 |
| Validation | Eight one-row invalid files plus separate whole-file cases | Each rejected atomically with correct reason; the valid main file accepted |

The duplicate false positives are intentional semantic ambiguity: the candidate rule flags them by design. Show both views. Do not optimize the large pair denominator into a misleading headline. Operational workload is 12 duplicate candidate groups plus 20 mismatch findings for human inspection.

## Workflow and robustness evidence

Verify repeated imports preserve the existing review state for the same hash/ruleset; changed file bytes create a new independent batch. Verify row order does not change group membership, restarting preserves review events, reopening appends history, and stale-tab submissions cannot silently overwrite decisions. Test escaped source text in rendered evidence and a failed import transaction. Separate a deliberately unsupported split-across-batches duplicate case and label the known limitation.

Planned evaluator output should contain fixture/version/hash, expected-label hash, ruleset, source revision, command, runtime/dependency versions, UTC run time, counts, metrics, unmatched finding identities, and failures. Save a machine-readable report plus a concise human summary. Have the owner reproduce it from a clean local environment after Claude's implementation is reviewed.

## Acceptance and interpretation

Stage 1 acceptance requires exact candidate-rule conformance, correct arithmetic findings, rejection behavior, and durable review workflow. An alert-only semantic duplicate score of 83.33% precision is expected on this deliberately difficult fixture; the two legitimate collisions demonstrate why humans must review. Actual results remain blank until execution. No result here supports real-world fraud detection, money saved, enterprise scalability, or private-customer accuracy.
